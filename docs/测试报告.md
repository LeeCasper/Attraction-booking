# 测试报告

景区预约管理及门禁联动系统 —— 各里程碑端到端验收测试记录。

- **测试方式**：端到端接口冒烟测试（真实调用运行中的服务端 + MySQL + Redis，非 mock）+ k6 性能压测
- **可重复性**：七套冒烟脚本与三套压测脚本均**状态无关、可重复执行**（每次运行使用独立的运行标识、日期区间与票种，不依赖数据库初始值）。`smoke:config` 会临时改动 `sys_config`，脚本在结束前（含异常路径）一律还原
- **执行命令**：`cd server && npm run smoke` / `smoke:order` / `smoke:gate` / `smoke:m4` / `smoke:visitor` / `smoke:date` / `smoke:config`；压测见 `npm run loadtest:booking` / `loadtest:oversell` / `loadtest:gate`

> ⚠️ **`smoke:m4` 里「承载量超阈值触发分级告警」这条有前置条件**：它把景区承载量临时设成 1，
> 然后等定时任务报警 —— 但报警条件是 `在园人数 / 承载量 ≥ 0.8`，**在园人数为 0 时永远不会触发**。
> 而在园人数是「今日入园 − 出园」，跑完 `smoke:gate` 后往往正好抵消成 0。
> 实测：在该用例前手动把在园人数置为 > 0，任务 70 秒内即报出 `capacity_100`（功能本身正常）。
> 二义性在于它对「今日已有承载量告警」会走另一条去重分支 —— 所以这条**在干净库上会失败**，
> 想要稳过要么先造一个在园人数，要么当日已触发过一次。改脚本时别把它当成回归信号。

> ⚠️ **`smoke:m4` 还有一条**同理：「运营分析：不传 areaId 的收入 = 各景区之和」只有在
> **没有孤儿订单**时才成立 —— 景区被硬删之后，它的历史订单仍带着那个已删的 `scenic_area_id`，
> 「全部」算得到、逐景区求和（遍历现存景区）算不到，差额恰好是那部分。
> 本机删掉示例景区（id=1）后差额 1,136,000 分。这条**不改成 ≥**：它指向的是真问题。
> 已经修了「新删的景区不再产生孤儿」（`removeArea` 有引用就 409），存量那 186 张订单要不要清是运维决定。

## 2. 关键用例明细

### 2.1 M1：认证与权限（25 项）

重点断言：

- 错误密码被拒绝；**连续 5 次错误锁定 15 分钟**
- 超管登录返回权限 `["*"]`
- 未带 token 访问被拒 401
- **RBAC 越权拦截**：检票员查询库存 403、调整库存 403
- 库存调整不得低于「已售 + 锁定」（400）
- 重复生成库存幂等（第二次新增 0 条）
- 操作日志完整记录登录/生成/调整

### 2.2 M2：防超卖与支付（28 项）

| 用例 | 验证内容 |
| ---- | -------- |
| 下单锁库存 | Redis 预减生效，余票 −1 |
| 金额计算 | 订单金额 = 当日票价 × 人数 |
| 支付回调幂等 | 首次 `alreadyHandled=false`，重复 `true`，库存不重复扣转 |
| **并发防超卖** | **库存 3、并发 6 单 → 恰好 3 成功 3 拒绝；`locked + sold == total`，账目自洽** |
| 每证每日限购 | 同证件同日重复下单被拒 |
| 取消订单 | 锁定库存释放，重复取消被拒 |
| 退款 | 提前 30 天免手续费；审核通过后订单状态 60、库存回流；重复审核被拒 |

> 并发用例是防超卖方案的核心验证：Redis Lua 预减拦截 + MySQL 乐观锁兜底，两者叠加后在 6 抢 3 的竞争下未出现超卖，且数据库账目与总库存严格一致。

### 2.3 M3：凭证、闸机与核销（34 项）

| 用例 | 验证内容 |
| ---- | -------- |
| 闸机签名 | 错误密钥签名被拒 401 |
| **防重放** | 同一 nonce 二次请求被拒 401 |
| 规则下发 | 心率返回规则版本；规则拉取含凭证密钥、当日白名单 |
| 动态凭证 | 领取 token（60 秒有效），返回剩余可入园人数 |
| 核验开闸 | 返回 `open=true` + `cmdId` + 游客姓名 + 剩余人数 |
| **部分核销** | 2 人订单分两次核销，剩余数递减至 0 |
| **重复核销** | 第三次核验返回 `ALREADY_VERIFIED` 并产生告警 |
| 在园人数口径 | 仅核验**不**计入；通行回执后 +1；出园回执后回到原值 |
| 时段校验 | 出园闸机做入园核验 → `GATE_NO_PERMISSION` |
| 日期校验 | 非预约日期 → `WRONG_DATE` |
| 离线同步 | 已核销票的离线记录标记为冲突（以首次核销为准），不重复计数 |
| 看板 | 在园人数、承载率、闸机在线率、分时趋势（24 点）、日统计重算 |

实测性能：模拟器扫码 → 核验 → 返回开闸指令 **39ms**（设计目标 < 1s）。

### 2.4 M4：分析与运维（25 项）

| 用例 | 验证内容 |
| ---- | -------- |
| 趋势 | 返回连续日期序列（无数据补 0），含核销率与退款 |
| 转化指标 | 核销率 / 爽约率 / 退单率均返回 |
| 客流 | 分时 / 按日 / 按月三种粒度可用 |
| 财务 | **实收 = 收入 − 退款**（恒等式校验） |
| 报表导出 | 5 类 CSV 均可下载，含 UTF-8 BOM 与表头（订单 60 行、通行 110 行等真实数据） |
| 对账 | 三方数据返回完整；重复执行幂等；差异明细结构正确 |
| 备份 | mysqldump + gzip 成功，文件可下载（gzip 响应头） |
| **承载量预警** | 临时把承载量调到 1 → 60 秒内自动触发 `capacity_100` 分级告警 → 还原配置 |

## 3. 性能压测（k6）

脚本位于 `server/loadtest/`，用法、参数说明与完整解读见 `server/loadtest/README.md`。
环境为**单实例生产构建**（`npm run build && npm start`），本机 32 核，
MySQL 8 + Redis 7 跑在 Docker。

### 3.1 防超卖（最高优先级：超卖是业务事故）

| 场景 | 下单成功 | 被挡下 | 库存行终态 | 结论 |
| ---- | -------- | ------ | ---------- | ---- |
| 200 人抢 50 张 | 50 | 150 | `total=50 sold=0 locked=50 available=0` | ✅ 恰好等于 K |
| 1000 人抢 100 张 | 100 | 900 | `total=100 sold=0 locked=100 available=0` | ✅ 恰好等于 K |

「成功数 == K」由 k6 阈值硬保证，少卖一张同样判失败。被挡下的请求全部是
HTTP 4xx + 业务错误码（余票不足），无一例 5xx。

### 3.2 闸机核验链路（设计目标 §5.3：核验 <500ms、开闸 <1s）

| 场景 | 核验 P50 | 核验 P95 | 开闸链路 P95 | 看板 P95 | 结论 |
| ---- | -------- | -------- | ------------ | -------- | ---- |
| 40 并发刷码（≈ 真实部署的 40 个闸机位） | 80ms | 99ms | 190ms | 6ms | ✅ 达标 |
| 300 并发刷码（≈ 7 倍真实规模） | 370–423ms | **433–497ms** | 673–844ms | 45–55ms | ✅ 达标 |

300 次核验全部开闸成功，**在园人数净增恰好 300**（与通行回执一一对应）；
无效凭证拒绝路径 399 次全部返回业务错误码，零 5xx。

### 3.3 预约并发（设计目标 §8.1：1000+ 并发零超卖）

| 场景 | 下单 P50 | 下单 P95 | 吞吐 | 正确性 |
| ---- | -------- | -------- | ---- | ------ |
| 1000 并发 / 单一热点库存行 | 4.1–4.3s | 6.4–6.7s | 113–117 QPS | ✅ 1000/1000 成功，零拒绝零 5xx |
| 1000 并发 / 分散 5 个库存行 | 1.3–1.7s | 1.9–2.5s | 282–284 QPS | ✅ 1000/1000 成功，零拒绝零 5xx |

**解读**：设计文档对下单链路的要求是**容量与正确性**（1000+ 并发零超卖），这一条成立。
下单时延本身不是设计指标，且本数字来自**单实例**，还含有 k6 客户端调度开销
（`iteration_duration` 与 `http_req_duration` 的差值）。真正的容量约束是
**单个热点库存行的 InnoDB 行锁**：所有买家买同一时段时事务被串行化，
吞吐只有分散到 5 个时段时的约 40%。高峰开票时按更多时段分摊库存即可显著抬高上限。
连接池 `DB_POOL_SIZE` 调大到 100 实测无改善（P50 3.2s → 4.3s），瓶颈不在池。

### 3.4 压测发现并修复的缺陷

这两个缺陷只有并发压测能暴露，冒烟测试（串行调用）无法触发：

| # | 缺陷 | 影响 | 修复 |
| - | ---- | ---- | ---- |
| 1 | 并发重复核销抛 `QueryFailedError` 未捕获 | 两个通道同刻扫同一张票 → **HTTP 500**，而设计 §5.3 要求返回「重复核销」错误码 + 告警（PRD A-033） | `verify.service.ts` 增加 `isDuplicateKeyError()` 分支，把唯一索引冲突转成业务拒绝 |
| 2 | 模拟支付交易号 `mock_txn_${Date.now()}` 同毫秒撞键 | 并发模拟支付 → `payment.uk_transaction` 冲突 → HTTP 500 | `mini.controller.ts` 交易号追加随机后缀 |
| 3 | 重复核销重复写通行记录 | 一次重复刷码在 `passage_record` 留两条拒绝记录，看板「拒绝通行」计数翻倍 | 收敛到唯一的 `duplicated()` 出口 |
